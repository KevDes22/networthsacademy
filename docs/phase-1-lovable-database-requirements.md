# Phase 1 Lovable database and Storage requirements

Apply these changes through the Lovable editor on an isolated environment first. The repository's database migrations and generated types are managed by Lovable. The current feature branch contains application code only.

## Lovable implementation prompt

Implement the following against the existing `courses`, `course_sections`, `course_lessons`, role helper, and `academy-course-materials` bucket. Preserve IDs, content, assignments, and existing learner access boundaries. Keep RLS enabled. Generate and sync migrations and database types in Lovable.

### Curriculum integrity

- Replace the composite lesson-to-section foreign key's cascading delete with `ON DELETE RESTRICT`, keeping the same `(section_id, course_id)` relationship. Preserve the relation's validation and index coverage. Make course deletion explicitly reject courses containing lessons. Keep the current role checks and empty-section delete policy. Test an empty section deletion racing a new lesson insert. Either the insert succeeds and deletion fails, or deletion succeeds and insertion fails.
- Add database guards that keep `id`, `course_id`, `created_by`, and `created_at` immutable on section updates. Also keep `section_id` immutable on lesson updates. Enforce signed-in creator identity on both inserts. Continue to enforce current assignment and roles in RLS. Recheck permissions under the same course lock for operation functions. Cover account reassignment racing a write.
- On lesson inserts require `draft`. Enforce the transition matrix on every update using the old and new row. Assigned instructors may change their course's existing draft to draft or review. Administrators may keep state, submit or publish drafts, publish or return review items, and return published items to draft. Preserve database-managed `updated_at` for conditional writes. Ensure the revision advances strictly per row or introduce a version counter and update the app accordingly.
- Validate completeness at both `in_review` and `published`, including whitespace-only article content, HTTPS video link or supported uploaded video, and eligible attached resource. Validate URLs without fetching them and reject credentials, malformed URLs, and whitespace. Use the application's MIME allowlist in `src/lib/academy-curriculum.ts`, including the video subset, and require a positive size within the effective configured limit. Keep file metadata all-or-none. Validate the exact four-segment path with UUID owner and object key, matching course and lesson IDs. New references must belong to the authenticated uploader and refer to an existing object whose stored size and MIME match. Preserve an unchanged, valid attachment from a previous editor after reassignment. Ensure returning a lesson to draft is possible when its attachment needs repair.

### Ordering and section deletion

- Create authenticated RPCs for appending a section, appending a draft lesson, and swapping adjacent siblings. Suggested reorder signature is `move_course_content(kind text, id uuid, direction text, expected_neighbor uuid)`, returning whether the move occurred. Accept only section or lesson and up or down. Derive the course and section from the target row and verify them after locking. Take a per-course lock on the course row, shared by appends and curriculum mutations affecting the order, membership or status. Read siblings ordered by position, creation time and ID. Reject stale neighbor IDs and return a no-op for a current boundary. A section swap stays within the course. A lesson swap stays within the section. An instructor can only swap two adjacent draft lessons from their assigned course. Administrators can swap adjacent lessons in any state.
- Protect ordering fields at the database boundary from direct authenticated writes outside the approved functions. Use unique positions per course for sections and per section for lessons after inspecting existing duplicates. If a unique constraint is deferred for swaps, defer it in the reorder transaction. Perform both position writes in that transaction and roll back on any failure. Append under the same lock using the next position. Preserve gaps on deletion and avoid automatic renumbering. Supply a read-only collision report and obtain approval before repairing existing positions. Verify duplicate, stale, simultaneous and mid-transaction failure cases.
- Use invoker functions where possible. If privileged functions are needed to narrow table-level access, use a fixed search path, schema-qualified names, an explicit verified `auth.uid()` and role/assignment check before data access, and least-privilege grants. Revoke execution from PUBLIC and anon. Restrict authenticated direct insert/update privileges to operations or columns that cannot bypass guards. Preserve role and course assignment restrictions.
- After the restrictive foreign key is live, wire up an authenticated delete-empty-section server function that verifies assignment or administrator access, confirms deletion returned the row ID, and handles a concurrent insert as a conflict. Restore the confirmation dialog and ordering controls only after the generated RPC types and isolated checks are available.

### Private file lifecycle

- Verify the bucket exists, is private, and has the MIME allowlist and an explicit effective size cap no greater than 262144000 bytes. Check project-wide Storage and upload limits and hosted proxy limits. Configure the app and its documentation to match the verified cap. Test a small upload and files around the actual limit. Evaluate authenticated resumable uploads for large materials within the supported hosting limits.
- Make staged object names immutable. Remove authenticated overwrite, move and delete privileges for this bucket unless an explicitly safe operation needs them. Prevent direct removal or substitution of referenced objects. Retain exact owner/course/lesson/status checks for staging inserts. Restrict ordinary object reads to current authorised managers and referenced or own staged objects as needed to verify a save. Current signed downloads use 60-second tokens.
- Maintain a durable staging record or equivalent lifecycle state. Serialize attachment promotion and cleanup reservation for each object so a file queued for deletion cannot subsequently be attached. When a lesson detaches or replaces a file, or is deleted, queue the old path in the same database transaction. A scheduled worker should also find expired staged uploads after a grace period and reserve them through the same reference checks. Use the Storage API for deletion and record retry state. Use workload credentials only in the managed worker. Preserve all active references, even on timeout or repeated execution. Alert on deletion failures and referenced objects missing from Storage. Inspect legacy orphan and missing-object reports before authorizing cleanup.
- Treat stored MIME as transport metadata. Confirm that Storage enforces type restrictions and choose content inspection or quarantine where file safety requirements call for it. Continue serving downloads with attachment disposition and avoid inline HTML and document rendering.

### Verification and handoff

Use disposable administrator, assigned and unassigned instructor, and learner accounts in an isolated environment. Exercise both the application and authenticated database/Storage APIs. Verify role escalation and cross-course transfers are denied, locked and published lesson bodies cannot be changed by instructors, both review states require valid content, and direct file mutations cannot break references. Test replacement, failed metadata writes, ambiguous network outcomes, interrupted uploads, reassignment, deletion and repeat cleanup. Verify signing, expiry and unauthorised access with test assets. Record the actual environment, tests and outcomes before reporting production readiness.

Persistent review comments, reviewer identity, submission/review/publication timestamps and audit history are follow-up schema proposals. If approved, use a separate append-only event table tied to the same status transaction. No review history is currently recorded by this branch.
